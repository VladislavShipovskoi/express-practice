## 1. Критичные баги в коде

**1. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/books.js:124` — `getById` не `async` и не делает
`await`.**
`const book = getByIdBase(id)` — это Promise, он всегда truthy, поэтому ветка 404 недостижима,
а `res.json(book)` отдаёт `{}` с кодом 200. `GET /api/books/:id` фактически не работает.
→ `const getById = async (req, res) => { const book = await getByIdBase(id); ... }`.
*Проверено: 200 с телом книги для существующего id, 404 `{"message":"Book not found"}` для
несуществующего.*

**2. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/books.js:158` — `create` не делает
`await createBase(req)`.**
Ответ `201 {}` (пустой объект — сериализованный Promise), книга при этом создаётся «когда-то потом».
Ошибка сохранения не попадает в `catch`, а становится unhandled rejection.
*Проверено: 201 и полное тело созданной книги.*

**3. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/books.js:167` и `:184` — `update` / `deleteById`
вызывают `*Base` без `await`.**
Обёртка `try/catch` бесполезна: синхронно ничего не бросается. При ошибке БД запрос зависает без
ответа (клиент висит до таймаута), а Node пишет unhandled rejection. Во всех четырёх хендлерах
(`getById`, `create`, `update`, `deleteById`) нужен `async` + `await`.
*Проверено: PUT сохраняет изменения и отвечает 200, DELETE отвечает `{"status":"ok"}`,
повторный DELETE — 404; unhandled rejections не появлялись.*

**4. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/auth.js:18` и `:30` — `next is not defined`.**
`register` объявлен как `(req, res)`, `logout` — как `(req, res)`, но внутри колбэков
`req.login` / `req.logout` используется `next(err)`. Это `ReferenceError` внутри асинхронного
колбэка: Express его не перехватывает, обработчика `uncaughtException` нет → падение процесса
при первой же ошибке входа/выхода. → добавить `next` в сигнатуру обоих хендлеров.
*Проверено: при ошибке `req.logout` и при ошибке `req.login` вызывается `next(err)`,
исключение не бросается; ветка `catch` в `register` по-прежнему редиректит на `/register`.*


**5. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `counter-service/index.js:17-27` — сервис читает и пишет
произвольные ключи Redis, в том же Redis и том же db 0 лежат сессии (`index.js:36`,
префикс `session:`).**
Проверено вживую: `GET /counter/session:REVIEWFAKESID` вернул
`{"bookId":"session:REVIEWFAKESID","count":"{\"cookie\":...,\"passport\":{\"user\":\"...\"}}"}`.
Порт `3001:3001` проброшен на хост во всех трёх compose-файлах → неаутентифицированный доступ
к содержимому сессий (id пользователя, cookie-настройки) и возможность портить/создавать ключи
через `POST /counter/<что угодно>/incr`. → префикс для счётчиков (`views:${bookId}`), валидация
`bookId` как ObjectId, отдельная БД Redis (`/1`) или отдельный инстанс, порт не публиковать.

*Что сделано:* ключи счётчиков переведены в пространство имён `views:${bookId}`; `bookId`
валидируется как 24-символьный hex, иначе `400 {"error":"Invalid bookId"}`; `POST .../incr`
заодно возвращает счётчик (`{ status, count }` — раньше результат `INCR` выбрасывался);
порт counter-сервиса во всех трёх compose-файлах переведён на `127.0.0.1:3001:3001` — из внешней
сети он недоступен, локальная отладка осталась.

*Проверено вживую* (Redis в контейнере + запущенный `counter-service`): `GET` и `POST` на
`session:REVIEWFAKESID` → `400 {"error":"Invalid bookId"}`; валидный ObjectId → `count: 1`,
два `incr` → `count: 1` и `count: 2`, повторный `GET` → `"2"`; `redis-cli keys *` даёт ровно два
ключа — `views:<id>` и нетронутый `session:REVIEWFAKESID` с исходным значением.

*Побочные эффекты:* счётчики, накопленные под «голыми» ключами `<bookId>`, больше не читаются
(отсчёт для таких книг начнётся с 1) — миграция не делалась, в текущем Redis данных нет.
Отдельная БД (`/1`) не включена: после введения префикса она не обязательна, но остаётся доступной
как дополнительная изоляция. Открытыми остаются п. 18 (нет error-handler) и п. 24–25
(нет слушателя `'error'` и `catch` у `connect()`).

**6. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `middleware/file.js:8` — имя загружаемого файла
не санируется.**
multer 2.2.0 передаёт `originalname` из busboy как есть (`multer/lib/make-middleware.js:186`),
а disk-storage делает `path.join(destination, filename)` (`multer/storage/disk.js:36`).
Проверено: `originalname = "a/../../../views/main.ejs"` → итоговый путь `views\main.ejs`,
то есть перезапись EJS-шаблона загруженным содержимым = выполнение произвольного кода на сервере.
→ `path.basename(file.originalname)`, фильтр символов, и лучше — собственное имя
(`crypto.randomUUID() + ext`), а оригинал хранить только в БД.

*Что сделано:* имя на диске собирает `safeName()`: `path.basename` → вырезание управляющих
символов → whitelist `[^\p{L}\p{N}._-]` заменяется на `_` → серии точек схлопываются → stem
режется до 100 символов, расширение до 10 и приводится к нижнему регистру. Разделители пути
не проходят ни в одном виде, префикс `Date.now()` сохранён. Добавлен `defParamCharset: "utf8"`:
busboy по умолчанию декодирует параметры multipart-заголовков как latin1, из-за чего русские имена
превращались в `Ð_Ð½Ð_Ð³Ð_` и новым фильтром выбивались в подчёркивания. `safeName` дополнительно
экспортирована, чтобы её можно было тестировать изолированно.

*Проверено настоящей загрузкой* через реальный multer (POST multipart на тестовый роут с
`fileUpload.fields([...])`): `a/../../../evil-verify.js` → `public\img\<ts>-evil-verify.js`,
`..\..\..\views\main.ejs` → `public\img\<ts>-main.ejs`; ни одного файла вне `public/img` не
появилось, `views/main.ejs` не изменён; `Книга о книгах.pdf` → `<ts>-Книга_о_книгах.pdf`.

*Что осталось:* п. 13 — `limits` и `fileFilter` по-прежнему не заданы, поэтому размер файла не
ограничен, а `.js`/`.html`/`.svg` в `public/img` остаются допустимыми; п. 14 — файлы по-прежнему
лежат в публично отдаваемом каталоге.

**7. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/books.js:44` — `findByIdAndUpdate(id, bodyData)`
без опций.**
Возвращается документ ДО обновления → `PUT /api/books/:id` отдаёт устаревшие данные,
а `updateFormSubmit` редиректит на страницу с неверным состоянием. Валидаторы схемы не запускаются.
→ `{ new: true, runValidators: true }`.

*Проверено:* `updateBase` теперь передаёт в `callbackSuccess` документ с уже изменённым `title`
(прогон на заглушке модели, которая учитывает опцию `new`).
*Оговорка:* `runValidators: true` пока почти ничего не проверяет — в `models/book.js` нет ни одного
валидатора (п. 36). Опция заработает в полную силу после появления `required` / `maxlength`.

**8. `[крит]` ✅ ИСПРАВЛЕНО 2026-09-30 · `api/ui.js:50-53`, `:94`, `:110` — UI-хендлеры не ждут
асинхронные `*Base`.**
`createFormSubmit` делает `res.redirect("/")` до того, как книга сохранена (в списке её может ещё
не быть); `deleteById` и `updateFormSubmit` — та же схема. Ошибки становятся unhandled rejection,
страница остаётся без ответа. → `async` + `await` + `try/catch` с передачей ошибки в `next`.

*Что сделано:* все три хендлера стали `async` и ждут `createBase` / `deleteByIdBase` /
`updateBase`. Явный `try/catch` не добавлялся: Express 5 сам передаёт rejected promise
асинхронного хендлера в `next(err)`, и остальные хендлеры этого файла (`index`, `view`,
`updateForm`) написаны так же — поведение во всём файле осталось единым.

*Проверено:* в `save()` и `deleteOne()` заглушки была искусственная задержка 40 мс — к моменту
`res.redirect` книга уже лежала в хранилище (create) и уже была удалена (delete);
`updateFormSubmit` редиректит на `/book/<id>` с актуальными данными (следствие п. 7);
ошибка БД пробрасывается наружу (`mongo is down`), а не глотается; unhandled rejections не появлялись.

## 2. Безопасность

**9. `[выс]` Нет авторизации по владельцу.** Любой аутентифицированный пользователь может
редактировать и удалять любые книги (`routes/ui/book.router.js:6`, `api/books.js`). В `Book` нет
поля автора/владельца, сравнения `req.user._id` с владельцем нет нигде. Для учебного проекта это
главный архитектурный пробел в модели доступа.

**10. `[выс]` Удаление книги — GET-запрос.** `routes/ui/book.router.js:29` + кнопка
`views/books/view.ejs:33` с `window.location.href='/book/<id>/delete'`. Побочный эффект на GET
срабатывает от превью ссылок в мессенджерах, prefetch браузера, краулеров. → форма `POST`
(или `DELETE` из JSON API).

**11. `[выс]` `GET /logout`** (`routes/ui/user.router.js:11`) — выход выполняется по загрузке
картинки/ссылки с чужого сайта. → `POST /logout`.

**12. `[сред]` Нет CSRF-токенов.** Частично прикрыто `sameSite: true` → `SameSite=Strict`
(проверено по `node_modules/cookie/index.js:276-284`), но у Strict своя цена: при переходе
по внешней ссылке cookie не отправляется и пользователь выглядит разлогиненным. Разумный баланс —
`Lax` + CSRF-токены на все mutating-запросы.

**13. `[выс]` Нет ограничений на загрузку файлов.** `middleware/file.js` — ни `limits`
(размер, количество полей), ни `fileFilter` (тип/расширение). Принимаются файлы любого размера
(исчерпание диска) и любого типа. SVG/HTML, отданные с того же origin через `express.static`,
дают stored XSS. → `limits: { fileSize: ... }`, whitelist расширений и MIME.

**14. `[выс]` Загруженные файлы книг публично доступны без авторизации.**
`GET /api/books/:id/download` закрыт `isApiAuthenticated`, но тот же файл лежит в
`public/img/...` и отдаётся статикой (`index.js:57`) без всякой проверки. Имя вида
`1790773800118-orig.pdf` частично предсказуемо (timestamp + исходное имя). Хранение файлов книг
вне `public/` (или отдача только через хендлер с проверкой прав) закрывает и п. 6.

**15. `[сред]` Нет security-заголовков и rate limiting.** Отсутствует `helmet`
(CSP, `X-Content-Type-Options`, `X-Frame-Options`), `app.disable("x-powered-by")` не вызван
(Express виден в заголовках), нет `express-rate-limit` на `/login`, `/register` и на JSON API →
возможен перебор пароля.

**16. `[сред]` Конфигурация сессий захардкожена.** `index.js:21` — `SECRET || "TEST_SECRET"`:
тихий небезопасный дефолт вместо падения (в compose fail-fast уже есть, а при локальном
`npm run server` — нет). `index.js:43` — `secure: false` без переключателя по окружению.
Нет `app.set("trust proxy", ...)` → за реверс-прокси secure-cookie не заработает, а IP в логах
будет адресом прокси.

**17. `[сред]` Обработчики ошибок отдают то лишнее, то ничего.** `middleware/error.js` шлёт
`err.message` клиенту и не проверяет `res.headersSent` (ошибка после начала отправки ответа →
новый crash); подробности о БД и путях не должны уходить наружу. Обратная проблема в JSON API:
`res.status(500).json(e)` (`api/books.js:120`, `:136`, `:154`, `:163`, `:180`, `:196`) отдаёт
буквально `{}`, потому что `message` и `stack` у `Error` неперечислимые — проверено:
`JSON.stringify(new Error("boom")) === "{}"`. То есть клиент не получает ни причины, ни типа ошибки.
→ единый формат ответа `{ error: "CODE", message: "..." }` + корреляционный id в логе.

**18. `[выс]` В `counter-service` нет error-handler вообще.** Проверено вживую: на ошибке Redis
Express отдаёт HTML с полным стектрейсом и абсолютными путями
(`Error: ERR value is not an integer...` + `C:\Users\...\@redis\client\dist\lib\RESP\decoder.js`).
→ 4-аргументный обработчик, возвращающий JSON без стека.

**19. `[выс]` `counter-service/Dockerfile:3` — `ARG NODE_ENV=production` вместо `ENV`.**
ARG живёт только на этапе сборки: проверено отдельным `docker build`, в runtime
`process.env.NODE_ENV === undefined`. Значит Express в контейнере работает в development-режиме —
стектрейсы наружу (усиливает п. 18), кэш видов отключён. В корневом `Dockerfile:3` — правильный `ENV`.

**20. `[выс]` `mongo-express` опубликован на хост во всех трёх вариантах** (`8081:8081`),
включая прод, со статическими `mongoexpressuser` / `mongoexpresspass` прямо в файле.
Это полный доступ ко всей базе (пользователи, хеши паролей, сессии) с любого хоста сети.
→ в prod-варианте сервис не нужен, в dev — публиковать на `127.0.0.1:8081:8081`.

**21. `[сред]` Секреты в compose в открытом виде.** `MONGO_INITDB_ROOT_PASSWORD: example` и
креды внутри `DB_URL` / `ME_CONFIG_MONGODB_URL` не вынесены в переменные, хотя для `SECRET`
паттерн `${SECRET:?...}` уже применён. → тот же подход для всех секретов + `.env.example`.

**22. `[выс]` dev-вариант пробрасывает БД наружу без пароля.**
`docker-compose-dev.yaml:9` — `6379:6379` (Redis без `requirepass`), `:22` — `27017:27017`.
В любой публичной сети это открытый доступ к сессиям и данным. → `127.0.0.1:6379:6379`
или не публиковать вовсе (из хоста в контейнер можно ходить через `docker exec`).

**23. `[низ]` `views/main.ejs:6` — Tailwind с CDN без `integrity`/SRI и без локального fallback.**
`@tailwindcss/browser@4` — инструмент для прототипов, не для production; при отсутствии интернета
в контейнере весь UI теряет стили.

## 3. Надёжность и обработка ошибок

**24. `[выс]` Нет слушателя `'error'` у Redis-клиентов** (`index.js:27`,
`counter-service/index.js:7`). node-redis — EventEmitter: потеря соединения в runtime эмитит
`error`, а без слушателя это uncaught exception → падение процесса. Нужен
`redisClient.on("error", ...)` + стратегия переподключения.

**25. `[сред]` `counter-service/index.js:11-13`** — `await redisClient.connect()` в IIFE без
`catch` → unhandled rejection при недоступном Redis; `app.listen` стартует независимо от
состояния подключения, поэтому запросы падают с малопонятной ошибкой.

**26. `[сред]` `index.js:149`** — `server.listen` без обработчика `'error'` (занятый порт =
crash со стектрейсом вместо внятного сообщения). Нет graceful shutdown: на SIGTERM
(`docker compose stop`) соединения с Mongo/Redis не закрываются, а обработчиков сигналов нет
ни в `index.js`, ни в `counter-service/index.js`.

**27. `[выс]` `middleware/logger.js:9-10` — `throw error` внутри колбэка `fs.appendFile`.**
Ошибка записи (read-only ФС, заполненный диск, нет прав) убивает процесс: `throw` в async-колбэке
не перехватывается Express. Плюс лог растёт без ротации, пишется в CWD (в контейнере — `/app`,
т.е. в слой, а не в volume), и в него попадает полный URL с query-параметрами. Для контейнера
правильнее писать в stdout и не вести собственный файл.

**28. `[сред]` `api/books.js:147` — `res.download(path, name, cb)` с `res.status(404).json()`
в колбэке.** Заголовки к этому моменту уже отправлены → `ERR_HTTP_HEADERS_SENT`. Если
`book.fileBook` пустой, `res.download(null)` бросает TypeError. Путь относительный — работает
только при CWD = корень проекта. → проверка существования файла (`fs.promises.access`) до вызова,
абсолютный путь через `path.resolve`, в колбэке — только логирование и `next(err)` при
`!res.headersSent`.

**29. `[сред]` `api/ui.js:72-84` — два последовательных `fetch` к counter-сервису без таймаута.**
Если counter-service не отвечает (а не отказывает в соединении), страница книги висит бесконечно:
`try/catch` тут не помогает, нужен `signal: AbortSignal.timeout(1000)`. Результат `incr`
выбрасывается, хотя он уже содержит счётчик → лишний round-trip и гонка между `incr` и `get`
(два одновременных посетителя увидят одно и то же число).

**30. `[сред]` ⛔ ОТКРЫТО (подтверждено прогоном) · `api/books.js:21` и `:98` — callback-стиль
в `*Base`.**
`updateBase(req, res, cbSuccess, cbError)` принимает `res` и не использует его; ветвление
«нашёл/не нашёл» размазано по колбэкам, из-за чего ошибки и теряются (п. 3, 8).
`api/books.js:26` — `if (book.id)` при ненайденной книге даёт TypeError на `null` вместо 404.
→ вернуть Promise (`return book` / `return null`) и оставить ветвление в хендлерах.
*Проверено 2026-09-30: после фикса п. 3 запрос `PUT /api/books/<несуществующий id>` больше не
зависает, но отвечает `500 {}` вместо `404 {"message":"Book not found"}` — ветка `callbackError`
в `update` по-прежнему недостижима.*

**31. `[выс]` `index.js:82-105` — `joinBookRoom` не проверяет аутентификацию.**
Session/Passport применены к handshake (`index.js:49-51`), но `socket.request.user` проверяется
только в обработчике `comment`. Любой анонимный socket-клиент может вступить в комнату
`book_<id>` и получить последние 100 комментариев. Отправка комментария неавторизованным
клиентом просто молча игнорируется — клиент не узнает об ошибке.
`socket.emit("error", ...)` (`index.js:132`) на клиенте никто не слушает → сообщение теряется.
→ проверка `socket.request.user` в `io.use(...)`, ack-колбэк или собственное событие
`commentError`, которое обрабатывает клиент.

**32. `[сред]` `index.js:86-88` и `:107-134` — нет валидации входных данных чата.**
`bookId` не проверяется на формат (мусорный id → CastError в лог), длина `text` не ограничена
(лимит только на уровне `maxHttpBufferSize` socket.io ≈ 1 МБ) → один клиент может забить БД
мегабайтными комментариями. Комментарии не удаляются вместе с книгой (нет каскада) → осиротевшие
документы и ключи счётчика.

**33. `[сред]` `middleware/error404.js` всегда отвечает JSON.** Обычный пользователь на
несуществующем URL видит `{"message":"Page not found"}`; HTML-шаблон `views/errors/404.ejs`
используется только для отсутствующих книг. → выбирать представление по заголовку `Accept`
(и отдавать HTML для браузеров).

**34. `[низ]` `index.js:19` — `DB_URL` без дефолта и без явной проверки.** При отсутствии
переменной `mongoose.connect(undefined)` падает с неочевидным сообщением, а `start()` печатает
`Failed to start server` и делает `process.exit(1)`. Лучше валидировать набор обязательных
переменных на старте одним списком и падать с понятным текстом.

**35. `[низ]` Счётчик «Views» увеличивается при каждом рендере страницы**
(`api/ui.js:72`) — включая собственные обновления страницы и ботов. Это «загрузки страницы»,
а не уникальные просмотры; стоит хотя бы назвать честно.

## 4. Модели и данные

**36. `[сред]` `models/book.js` — схема без типов и ограничений.** Все поля `String`, ни одного
`required`, нет `trim`/`maxlength`. `favorite: String` — из чекбокса приходит `"on"`
(в `views/books/form.ejs:58-67` значение не задаётся), поэтому в БД лежит строка вместо
`Boolean`. `authors: String` вместо `[String]`. Нет `timestamps` → нельзя сортировать список
по дате добавления и показывать её.

**37. `[сред]` `models/book.js` — нет `toJSON: { virtuals: true }`, поэтому JSON API не отдаёт `id`.**
Проверено: `Object.keys(new Book({...}).toJSON())` → `["title","authors","_id"]`. При этом вся
остальная система построена на виртуальном `id`: шаблоны (`views/books/view.ejs:17`, `:33`),
комнаты socket.io (`book_${bookId}`) и ключи счётчика. Клиент API получает только `_id` и не может
строить ссылки так, как это делает UI. → `bookSchema.set("toJSON", { virtuals: true })`
(и `toObject` при необходимости).

**38. `[низ]` `models/comment.js:3` — опечатка `commnetSchema`; `createdAt` задан вручную вместо
`timestamps: true`; у `text` нет `maxlength`; нет составного индекса `{ bookId: 1, createdAt: 1 }`
под запрос истории (`index.js:86-88`) — одиночный индекс по `bookId` не покрывает сортировку.

**39. `[сред]` `models/user.js` и `api/auth.js:11-25` — регистрация без валидации и без обратной
связи.** `email` без `lowercase`/`trim`/`match`, длина пароля не проверяется,
`UserExistsError` проглатывается в `catch` → редирект на `/register` без сообщения: пользователь
не понимает, что имя уже занято. То же при ошибке входа (`failureRedirect: "/login"` без причины).
→ flash-сообщения (`connect-flash`) или query-параметр `?error=...`, прочитанный шаблоном.

**40. `[низ]` Мёртвая логика сессий и гардов.** `middleware/isLoggedIn.js:6` пишет
`req.session.returnTo`, который нигде не читается → после логина всегда попадаешь на `/`.
`isLoggedOut` не подключён ни к одному роуту (проверено grep по `routes/`) → `/login` и `/register`
открываются залогиненному пользователю.

**41. `[сред]` Удаление книги не убирает связанные данные.** `api/books.js:98-113` удаляет только
документ `Book`: файлы `fileCover`/`fileBook` остаются в `public/img`, комментарии — в коллекции
`Comment`, ключ счётчика — в Redis. При обновлении с новой обложкой старый файл тоже остаётся.
→ `unlink` файлов в хендлере удаления/обновления + `Comment.deleteMany({ bookId })`.
